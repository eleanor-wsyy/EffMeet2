## 1. 问题清单

### 问题 1 · 红线：模型直接生成播报文案（必须改）

- **位置**：`_build_analysis_prompt`，输出指令第 2 行
- **现状**：要求模型生成"不超过 80 字的提示语（格式：线上成员提出：...，现场可以回应一下吗？）"
- **为什么是红线**：这段文字将直接进入机器人播报。报告"不允许"清单明确写有**"模型原话直接上设备"**；A/B 分工约定"A 负责文案，B 负责……安全校验"。模型的职责是给原料（观点转述），说什么话由固定模板决定——播报环节的即兴发挥空间必须为零。
- **改法**：`proposed_text` 重新定义为"≤30 字的观点转述，忠于原话"；完整播报句由服务端用模板拼接（模板见判断样例文档 §3.1：*"打扰一下——刚才线上成员提到〈摘要〉，现场可以回应一下吗？"*）。

### 问题 2 · 缺弃权规则（必须改）

- **位置**：`_build_analysis_prompt` 全文
- **现状**：只定义了任务（"判断是否已获得现场回应"），没有定义**何时必须输出 uncertain**。
- **风险**：模糊输入（混说、破碎转写、语义不清）下模型自由发挥，可能幻觉出"观点被忽视"的结论——而候选卡会把它弹给本人看，破坏"不确定则弃权"的产品承诺。
- **改法**：prompt 中加入触发条件清单（见 §2 替换文本规则 3–4）。

### 问题 3 · 缺"不判断对错"约束（必须改）

- **现状**：无任何立场约束，模型可能对观点内容发表评论（"这个观点很有道理……"），污染 `reason` 字段甚至 `proposed_text`。
- **改法**：规则第 1 条明确"只判断回应关系，不判断观点对错，不评价任何人"。

### 问题 4 · system prompt 过简（建议改）

- **现状**：`"你是一个会议内容分析助手。只输出JSON，不要输出其他内容。"`
- **改法**：补充角色边界与证据纪律（见 §2）。

## 2. 建议替换文本（B 直接采用）

**system prompt**：

```
你是会议讨论的分析助手。你的唯一任务是判断"线上成员的观点是否已有可关联的现场回应"。你不判断观点对错，不评价任何人，不生成任何建议。证据必须来自输入中的原始发言。只输出JSON，不要输出其他内容。
```

**`_build_analysis_prompt` 的输出指令段**（替换第 178–183 行）：

```
请以JSON对象格式输出：
- status: "responded" / "possibly_unresponded" / "uncertain"
- proposed_text: 仅当 status=possibly_unresponded 时，给出不超过30字的观点转述（忠于原话，不得改写立场，不要写成提示语或问句）；其他状态输出空字符串
- reason: 一句话判断依据（不超过100字），供事后审计

规则：
1. 只判断"是否已有可关联的现场回应"，不判断观点对错，不评价任何人
2. 关联回应需同时满足：时间在观点之后、语义明确指向该观点；仅仅话题相关不算回应
3. 证据不足、说话人不明、多人混说、转写破碎、语义模糊 → 一律输出 uncertain
4. 拿不准就输出 uncertain，宁缺毋滥
```

**配套代码修改**：

| 位置 | 现状 | 改为 |
|---|---|---|
| `_parse_analysis` 中 `proposed_text` 截断 | `[:120]` | `[:60]`（服务端双保险） |
| 播报文案生成 | 使用模型输出的提示语 | 服务端模板拼接：`f"打扰一下——刚才线上成员提到{proposed_text}，现场可以回应一下吗？"` |
| prompt_version 标记 | `"qwen-v1"` | `"qwen-v2"`（语义变更，版本号跟进） |

## 3. 遗留观察项（不阻塞，记入后续迭代）

1. **`response_utterance_ids` 粗放**：`status=responded` 时把全部现场发言标为回应。mock 阶段可接受；正式版应让模型标注具体回应句 ID（viewpoint prompt 已有 `response_evidence_ids`，analysis 侧对齐即可）。
2. **冷却与去重**：README 自述留给后续模块。A 侧建议值：同一观点仅提醒一次；两次播报间隔 ≥60 秒。排进 10.06 联调后的迭代。
