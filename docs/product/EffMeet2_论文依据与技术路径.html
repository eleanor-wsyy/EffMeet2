作品定位 / 为什么属于效率进化

修改 · 产品方案 桌面会议伙伴，围绕三个协作难点

EffMeet 2的产品形态是“固定式桌面机器人 + 远程辅助界面”。桌面设备承担现场感知与短提示，线上成员通过界面看图、确认介入和核对记录。首个验证场景为校园科研与课程项目讨论；效率进化赛道允许自由创作，使用千问不自动等于选择阿里云特别赛题。依据 R2

现场桌面伙伴

一台有明确职责的会议设备

机内麦克风、按需拍摄的摄像头、扬声器和单轴转头组成现场伙伴，以桌面宠物形态呈现。用户接电与Wi-Fi即可使用设备，不另接USB麦克风或外置音箱。固定底座便于携带与桌面摆放。

核心体验 / 单一场景 · 拟实现

一场讨论，串起三条功能线

演示设定：两位现场成员、一位线上成员，讨论同一份项目方案。视频时长由团队安排，官方已读要求没有规定必须90秒。

  1. 看见现场

    现场画草图，线上看不清

    抓拍并共享原图；千问视觉描述仅作辅助，线上成员可自行核对。

  2. 留下观点

    线上成员提出建议

    最终转写进入事件账本，保存发言人、时间与原文片段ID。

  3. 发现候选

    现场讨论继续，尚无明确回应

    规则筛选后，千问提出可能未被回应的观点，附证据与不确定状态；不直接判定“被忽视”。

  4. 本人决定

    线上成员选择“请提醒”或“不必提醒”

    本人确认后仍等安全停顿，执行前复核是否已得到回应；无确认不播报。

  5. 现场回应

    机器人短提示，现场成员接话

    播放及转头动作各留回执；AI推测的回应关系与本人核对的回应状态分开。

  6. 会后可核对

    生成观点与回应记录

    每项能返回原文；决策、归属或回应不明确时标注待核对。

初赛Demo可结合交互原型、功能样机与录像展示核心体验。各环节标注实时、人工或回放模式，便于评委理解展示范围。初赛要求 R1 §2.2.2

实施路线 / 产品主路与样机装配

修改 · 产品方案 路线A（Demo）：机内音频 + Wi-Fi + 电脑伴侣 + 云端理解

当前参赛形态（路线A）为“电脑伴侣型桌面会议机器人”：机器人负责感知和表达，电脑负责本地AI与编排，云端负责理解。正式使用接电、连Wi-Fi、打开伴侣应用并建会；用户不另接USB麦克风，不配置Python。最终产品形态（路线B）去除电脑依赖，机器人经Wi-Fi直连云端服务，仅需平板或手机参与。以下按功能装配，不以开发日期代替技术依赖。

01 两路输入线上与现场音频分开；现场草图按需抓拍
02 确认转写ASR 最终片段 + 手动发言人校正
03 事件账本会议/发言/图片/来源/时间/唯一 ID
04 千问候选阿里云百炼 DashScope API 调用（qwen-plus），产出观点、回应关系、证据 ID；不确定则弃权
05 本人确认线上本人“请提醒 / 不必提醒”；无确认不播报
06 机器人执行以宠物形态短句播报与回执；转头可后置
07 回应与总结现场回应绑定原观点；会后保留原文
正式产品音频

机内拾音和播放，共用可控音频链

样机优先采用ESP32-S3-Korvo-2音频板作为电路与驱动参考：板上麦克风经ES7210采集，ES8311承担播放Codec，配机内扬声器。正式版延续集成拾音/播放设计，再优化PCB与外壳；不把开发板直接宣称量产板。

ESP-SR AFE提供AEC、降噪等组件；B/C按实际板卡配置M/R通道。Korvo-2官方板采用Codec DAC输出回采为AEC参考，不能简单以“发送过的TTS数据”替代实际播放对齐。I²S是机内音频接口，双麦输入不自动等于多人分离或360°定位。依据 R7

明确的产品依赖

电脑跑AI，ESP32跑设备固件

Python + FastAPI + SQLite保留在电脑伴侣应用；本地FunASR接收归一化语音，千问通过阿里云百炼 DashScope API 分析候选与抓拍。发行时携带匹配运行环境、依赖和模型配置，由安装/启动入口管理；DashScope API Key 仅存服务端配置文件，不进前端、不打包进固件。ESP32-S3用ESP-IDF C/C++处理音频、配网、任务与动作。

不在首版承诺把FunASR和大模型塞进ESP32，也不临时增加机内Linux算力板。若后续需要独立整机，再按处理速度、功耗、散热、存储和成本评估算力模块。分层参照 R4

机内麦克风 → ES7210 / I²S采集 → AFE（麦克风 + 播放参考） → 16 kHz单声道PCM → Wi-Fi → 电脑ASR / 现场音轨 远程人声 / 经本人确认的TTS → Wi-Fi → 播放队列 → ES8311 → 功放 / 机内扬声器 └→ 实际播放参考送回AEC 按键静音 / 停止 ─→ 本地固件立即处理；不等待云端响应
远程语音主路

用自己的受控音频房间，明确两路来源

首版在EffMeet会议入口提供小组语音通道，采用LiveKit媒体SDK，不重做完整视频会议平台。远程网页经HTTPS授权麦克风并发布个人音轨；电脑媒体适配器订阅远程音轨用于ASR，并送机器人机内扬声器。机器人拾音经电脑发布为现场音轨，供远程成员收听。

事件/图片/本人确认走业务HTTPS/WSS；语音走WebRTC媒体通道，两者职责不同。远程身份来自房间授权映射，现场共享麦克风仍允许手动校正。所有机内播放进入AEC参考；关闭现场电脑重复外放，远程端建议耳机。依据 R8

测试适配器

USB与WASAPI只验证模块或兼容性

台架可用USB麦克风替代机内拾音，用电脑音箱替代机内播放，先测接口与候选逻辑；模块契约不随测试器材改变。黑客松样机装配时换回机内音频。WASAPI loopback只用于外部会议软件兼容试验，不能保证音频属于某位远程成员。

每个片段保留 event_id / meeting_id / seq / occurred_at / source / mode(real|manual|mock|replay)。转写含 utterance_id / speaker_id / channel / start_ms / end_ms / final / text；千问候选含 claim_id / evidence_ids / response_ids / status / reason。机器人动作含 command_id / intervention_id / requested / acknowledged / completed；所有总结项必须能返回原文片段 ID。

修改 下文统一字段以导出的v1 JSON Schema为准；HTTP提交的是请求DTO，控制器校验、落盘后生成EventEnvelope，C/D和relay不自行分配seq。mode增加replay以区分预录回放；真实来源标签不得由客户端随意伪造。

事件网关只同步授权事件、图片与确认；本地账本仍是主账本。新增的语音房间会传输经同意的实时音频，不能再笼统写“公网不传音频”。媒体默认不落原始录音；转写、图片与模型处理的保留/授权单独设置。

FINAL_UTTERANCE → REMOTE_CLAIM → CANDIDATE → WAIT_REMOTE_CONFIRM ├─ dismiss / timeout → CLOSED_NO_SPEECH └─ confirm → QUEUED → ROBOT_ACK → SPOKEN → WAIT_HUMAN_RESPONSE └─ fail → MANUAL_BACKUP WAIT_HUMAN_RESPONSE → AI_RESPONSE_CANDIDATE → HUMAN_VERIFIED / UNRESOLVED 不允许：ASR partial 直接触发播报；模型原话直接上设备； 没有原文 evidence_id 就标注“观点被忽视”；重连后重复播报同一 command_id。

候选触发（候选，不是判决）

只在最终转写、明确线上发言人、当前议题相同且尚无可核对回应时评估。规则先筛选；千问只判断“是否有关联回应”并引用发言 ID。模型自报置信度不能当校准概率；串音、说话人不明、语义模糊、会议已结束 → 不触发或显示“需人工核对”。冷却与单观点去重防止刷屏。

播报语气与时机

机器人以桌面宠物形态发出提醒，不是冷冰冰的系统通知。模板："刚才线上成员提到〈经本人确认的简短观点〉，现场可以回应一下吗？"不要求宠物假装脆弱、讲笑话或替人做决定。A 负责文案，B 负责证据、长度、安全校验、确认与回执。确认后仍等当前发言结束或安全停顿，执行前复核是否已经得到回应；候选过期就取消。机器人播报期间标记 robot_audio 并抑制其进入人声判断，避免自我触发。保留现场停止按钮。

新增 重试、权限与真实回执规则

  1. 同一utterance_id/command_id重试必须沿用原ID；相同ID不同内容返回冲突。设备收到已执行ID只返回既有回执，不再动作；boot_id变化后不自动重发旧speak。
  2. 命令返回202或accepted仅表示入队/接收；started、completed、failed由真实驱动或主机播放回调产生。ESP32不宣称它没有执行的语音完成，现场听证与软件完成回执分开。
  3. ttl_ms按设备接收后的单调计时执行，控制器不下发已过期任务；stop优先取消。服务端再次校验本人身份、状态revision、安全停顿、证据和设备能力；没有确认不发speak。
  4. 浏览器经HTTPS/WSS认证会话与Origin校验；不把令牌放URL，不开放机器人公网端口。现场网关出站连接；同Wi-Fi设备HTTP仅用于隔离并认证的演示网络，产品化TLS/签名仍需补齐。
  5. ASR本地二进制音频不装进公网事件的base64；图片/确认同步按原隐私与授权边界。mock/replay默认无真实硬件副作用；状态脸只呈现实际阶段。
  6. 修复性orient/light也绑定已批准intervention；只有预先允许的状态灯和安全stop可独立执行。设备地址来自配对表，hello不接受任意回调URL；设备重启须重新握手。

命名、配置与合入规范

  • 统一线格式：UTF-8 JSON，字段一律snake_case；事件用点分类型名（如utterance.final），身份使用会议内别名。内部TS变量可camelCase，适配层负责映射，网络上不出现两种字段拼法。
  • 单位与时间：ASR及机内传输归一化为16kHz/单声道/s16le；板卡AFE前可多通道，WebRTC音轨用SDK实际采样率后再转换。相对采样计数/毫秒与UTC事件时间分开；yaw_deg/duration_ms按校准表执行，实体限位优先。
  • 类型与错误：JSON Schema为唯一真源，B生成或核对Python/TS类型；ErrorResponse包含code、message、retryable、trace_id。400/422格式错，401/403身份错，409版本/状态冲突，503设备不可用。
  • 代码与配置：Python四空格/snake_case，TS两空格，C++沿设备项目格式；配置集中在.env.example与设备配置，禁止硬编码密钥、端口和公网端点。依赖版本由B按库支持范围冻结，不假定本机Python版本都兼容。
  • 模块交付最小包：实现、README、配置样例、输入/输出fixture、单测或自检、依赖锁/版本、已知问题和可复现步骤。每个模块先用FakeAdapter独立运行，再换真实服务。
  • 分支与合入：feat/a-policy、feat/b-core、feat/c-audio、feat/d-web、test/e-integration；PR写明契约版本、改动目录、测试与新增依赖许可。不得改生成文件或私增API字段；B统一集成，契约变化先协商再同时更新双方。
  • 许可台账：记录repo、commit、文件、复用方式（dependency/code/design_reference）、SPDX或许可范围、修改说明、模型/硬件另行授权。保留实际采用文件的许可/NOTICE；不能仅列项目名就称完成合规。

没有证明会议公平性

总发言时长的均衡指标：脆弱表达组与中性组无显著差异（P=0.88），两者相对沉默组更均衡；对不同人说话的均衡，脆弱表达相对中性也无显著差异（P=0.16）。论文 Fig. 2 / p. 6372

可迁移的是设计问题：机器人发言之后，人与人之间是否产生了更多有意义的回应？不是照搬研究中的“自我暴露、故事、幽默”台词。

实验的机器人在每轮结束时发言，话语等长且情境被严格设计；发言被研究者人工转写并编码为 comment / response（四名编码者 κ=0.92）。它没有训练或验证实时识别“被忽略观点”的模型，也没有测试混合会议、远程参与者、转头方向或机器人移动。研究者为游戏设计了失败情节并在结束后解释；我们的产品演示不应伪造机器人犯错或假装已经证实公平性提升。论文 pp. 6373–6374
